# Cloud-native Nayose: git, GitHub, Docker, and instant environments

## 1. Git & GitHub workflow (this repo, enforced)

**Branching — trunk-based GitHub Flow.** `main` is always deployable. Work on
short-lived `feat/<name>` / `fix/<name>` branches, open a PR, merge after the
gate passes. No long-lived branches, no gitflow ceremony — the repo is a
single small team.

**Commits — Conventional Commits** (already the house style):
`feat(ui):`, `fix(api):`, `refactor(synthetic):`, `docs:`, `test:`,
`build(docker):`. Scope = layer. Raise PRs with 1 logical change; land with a
squash merge so `main` history stays bisectable.

**The gate — one command, two places.** `python scripts/audit_repo.py`
(ruff, mypy, tsc, npm test, pytest incl. schema-contract, arch-contract and
frontend gate) is the definition of done:

| Trigger | Enforcement |
|---|---|
| Local dev | `python scripts/audit_repo.py` before pushing |
| CI push/PR | `.github/workflows/ci.yml` → `gate` job runs the same command |
| Rules files | `AGENTS.md` (contract) + `ARCHITECTURE.md` — CI is the drift-ring |

**GitHub settings checklist:**

- **Branch protection on `main`**: require PR, require the `Audit gate`
  status check, require up-to-date branch, disallow force-push.
- **Release**: tag `vX.Y.Z` on `main` → CI builds + pushes the GHCR image
  (`ghcr.io/<org>/nayose:vX.Y.Z`, `vX.Y`). `run_manifest.json` in each bundle
  already records config_hash + data_fingerprint — treat it as the model
  release manifest.
- **Dependabot** for `pyproject.toml` + `frontend/package.json` (+ npm audit
  alerting). Bump PRs run the same gate.
- **Secrets**: `NAYOSE_API_TOKEN`, `HF_TOKEN` go in GitHub Secrets / org
  secrets, never in the repo (`.env*` is gitignored; `.env.example` is the
  annotated template).
- **GitHub Actions** on this repo: `gate` (every push/PR), `data-smoke`
  (nightly + manual: generate → `scripts/train.py` → `audit_decisions.py`
  to prove the full contract in a fresh environment), `image` (on tags → GHCR).

**What never enters git:** `data/`, `models/` (regenerable, large — see
`.gitignore`), `*.executed.ipynb`, `.env`. `frontend/js/` **is** committed
(generated by `tsc`, per AGENTS.md: build & commit) — CI's `tsc` step keeps
it honest.

## 2. Do we need Docker?

**For running locally: no** — `venv` + the notebook generator work on any
machine. **For "runs everywhere instantly": yes.** The reasons are concrete:

1. **Runtime parity** — LightGBM needs `libgomp1`; the image pins
   `python:3.13-slim` + wheel versions; serving behaves identically on
   laptops, CI, VSCode devcontainer, Fly.io, ECS.
2. **Immutable images** — data/models are **volumes, not baked in**: the
   image never contains a snapshot, so one artifact serves every environment.
3. **Trusted entrypoint** — non-root `nayose` user with privilege-dropping
   entrypoint (`su-exec`), `HEALTHCHECK` on `/api/health`.
4. **CI artifacts** — the `gate`/`data-smoke` jobs run the identical build.

Build: `docker build -t nayose .` (or rely on the `vX.Y.Z` tag → GHCR).
Run: `NAYOSE_API_TOKEN=... docker compose up` (volumes `./data`, `./models`).

## 3. Cloud-native deployment

The workload is two long-running services with a volume dependency:

```
data/ (immutable generations + current alias) ─┐
                                               ├─→ api.main (FastAPI + DuckDB)
models/ (immutable runs + current + decisions) ─┘
train (batch, on GPU box): generate → scripts/train.py → promote models/current
```

Per-stage target:

| Stage | Where | How |
|---|---|---|
| CI gates | GitHub Actions | `gate` + `data-smoke` (free, linux runners) |
| Training | your dawnlight.net box, or any GPU runner | `docs/REMOTE_GPU.md`; artifacts → object storage |
| Serving | Fly.io / Render / ECS Fargate | one container, volumes for `data/`+`models/`, `NAYOSE_API_TOKEN`, healthcheck |
| Frontend | same container (`/static`, no build step) | URL-as-state + F1–F5 views already cached-friendly |

Minimal Fly.io example (`fly.toml` sketch):

```toml
app = "nayose"
[build]
  image = "ghcr.io/<org>/nayose:vX.Y.Z"
[env]
  NAYOSE_MODELS_DIR = "/models"
  NAYOSE_DATA_DIR = "/data/current"
  NAYOSE_API_TOKEN = "from-secret"
  NAYOSE_WARM_EMBED = "1"
[services]
  internal_port = 8000
  [[services.http_checks]]
    path = "/api/health"
[mounts]
  source = "models", destination = "/models"
  source = "data", destination = "/data"
```

Blob options for artifacts: S3/R2 for trained bundles (a `models/` sync step),
versioned by `run_<ts>_<hash>` + `current` symlink — the existing layout maps
1:1 to an immutable object store.

## 4. Run everywhere instantly (the matrix)

| Want | Do | Time |
|---|---|---|
| Identical dev box | Open repo in **VSCode Dev Containers** (`.devcontainer/`) — python 3.13 + deps + node, `postCreate` installs `.[matcher,neural,train,serve,dev]` | ~2 min |
| Local serving | `docker compose up` (image or build; mounts data/models) | seconds (after image) |
| Remote GPU training | `docs/REMOTE_GPU.md` on the 3090 box | clone + install + train |
| CI / nightly contract | GH Actions `gate` / `data-smoke` | automatic |
| Production | Fly.io/Render/ECS + tagged GHCR image + volumes + token | one deploy |

The invariant that makes all of this work: **everything is `NAYOSE_*`
env-configured, seed-reproducible, immutable (generation/bundle + `current`
alias), and contract-tested** — so the same artifact moves from laptop to GHCR
to Fly.io without a single code change.
